## 1. 结论摘要

- 你提出的 5 步流程**成立**，但需要补两个环节：**输入归一化**与**结果回灌**；
- 插件执行与嵌套由**宿主安排**，chatllm 只负责检索、选择建议、生成与持久化；
- 对话输入可分为 **7 类**（`I1–I7`），结构化数据单列；
- 输入方式当前基线 **7 种**（`CH1–CH7`），按阶段逐步增加，不含语音；
- 插件在流程中只按**三种角色**理解（`R1–R3`），业务分类暂不讨论；
- 插件嵌套允许 **5 层**，调用次数**不设上限**，单插件超时 **15s**；
- 最终呈现 = 主文本 + 附件 + 可选状态提示，由宿主渲染。

## 2. 你提出的流程

| 步骤 | 内容 |
| --- | --- |
| F1 | 内容输入 |
| F2 | 在本地创建一个对话 |
| F3 | 查找 plugin |
| F4 | plugin 又调用其它 plugin（需要设计约束） |
| F5 | 获取结果，并返回 |

## 3. 与现有实现对比

| 步骤 | 你的设想 | 现有实现 | 差异 | 建议归属 |
| --- | --- | --- | --- | --- |
| F1 内容输入 | 文本、文件、设计软件内容 | `post_chat` 只接收 `prompt` 文本 | 文件 / 设计软件上下文缺失 | 宿主归一化，chatllm 接收 `attachments` / `app_context` |
| F2 创建对话 | 本地创建对话 | `create_dialogue_with` 已支持自动 id、`dialogue_id`、`plugin_uuid` | 已具备 | chatllm |
| F3 查找 plugin | 按内容找能力 | 检索能力已移除 | 无内置检索 | 宿主 / 后续 kv_lib |
| F4 plugin 嵌套 | 插件调用其它插件 | 无执行与嵌套能力 | 完全缺失 | 宿主安排 |
| F5 返回结果 | 获取并返回 | `post_chat` 返回文本 + HTML | 插件执行结果未回灌，附件缺失 | chatllm 生成，宿主展示 |

### 3.1 修订后的流程

```text
F1  输入归一化（宿主）
     文本 / 文件 / 文件夹 / 设计软件上下文 / 媒体 / 结构化数据
        ▼
F2  创建或复用对话（chatllm）
     uuid / dialogue_id / plugin_uuid
        ▼
F3  检索与选择（宿主 / 后续 kv_lib）
     检索能力已从 chatllm 移除
        ▼
F4  执行与嵌套（宿主安排）
     入口插件 → 子插件（最多 5 层，次数不限）
        ▼
F4.5 结果回灌（宿主 → chatllm）
     tool_results + attachments
        ▼
F5  生成与返回（chatllm）
     content + attachments + 持久化
```

关键变化：F1 与 F4.5 是两个新增环节；F4 不进入 chatllm 内部，由宿主安排。

## 4. 对话输入类型（7 类）

| 编号 | 类型 | 判据 | 现状 | 处理方 |
| --- | --- | --- | --- | --- |
| I1 | 短文本 | 单条消息、通常 ≤ 2k 字 | ✅ 已支持 | chatllm |
| I2 | 长文本 | 超过模型上下文或 2k 字，需要预算 / 分块 | 🟡 可传入，无预算与分块 | 宿主 + chatllm |
| I3 | 单文件 | 一个可读文件（txt / md / pdf / docx / cdr / ai / ps） | ❌ 无文件读取 | 宿主解析；设计格式由插件导出 |
| I4 | 多文件 / 文件夹 | 两个以上文件，或目录 | ❌ | 宿主枚举与归一化 |
| I5 | 设计软件上下文 | 当前文档、选区、页面、版本 | ❌ | 宿主 / 插件采集 |
| I6 | 媒体 | 图片、音频、视频 | ❌ | 宿主；视觉推理待确认 |
| I7 | 结构化数据 | 表格、CSV、JSON、键值清单 | ❌ | 宿主解析；chatllm 只接收文本化结果 |

说明：

- 短文本与长文本是同一形态的两种规模，分开是因为预算与分块策略不同；
- `I7` 单列，不再并入文件；解析后通常转成文本表格或 JSON 摘要；
- `I3`、`I4`、`I7` 的文本都要受上下文预算约束；
- `I6` 是否直接进模型取决于视觉模型能力（契约 Q13）。

## 5. 插件在流程中的角色（暂不分类）

业务分类（文件、设计、系统、外部服务等）暂时不讨论。流程上只需要区分插件在调用链中的角色：

| 编号 | 角色 | 行为 | 副作用 | 嵌套 |
| --- | --- | --- | --- | --- |
| R1 | 检索型 | 只读查询，返回候选或数据 | 无 | 可自动，受深度与环约束 |
| R2 | 执行型 | 改文件、改设计软件、生成或转换 | 有 | 需宿主确认后执行 |
| R3 | 编排型 | 调用其它插件、串联多步 | 继承子调用 | 受深度、环约束 |

说明：

- `R3` 是“plugin 调用 plugin”的承载角色；
- 一个插件可以同时具备多种角色，按本次调用判断；
- 角色只用于流程约束，不替代 `plugin_functions.category`；
- 检索能力已从 chatllm 移除；`plugin_search` 也不再提供 `side_effects`。

### 5.1 三类角色对应的插件

> 具体名称以 `plugin_functions` 登记为准。当前代码中只确认了 `cdrimex` 一个示例，其余为能力形态，不代表已存在。

| 角色 | 内置 / 外部 | 具体内容 | 现状 |
| --- | --- | --- | --- |
| R1 检索型 | — | 检索能力已移除，由宿主 / 后续 kv_lib 承担 | ❌ 当前不可用 |
| R1 检索型 | 外部 | 设计插件中的查询能力：获取当前文档、对象列表、图层 / 页面信息 | 🚧 待登记 |
| R2 执行型 | 外部 | 设计软件操作：`cdrimex`（CorelDRAW）、Illustrator / Photoshop 对应插件 | 🟡 仅 cdrimex 示例 |
| R2 执行型 | 外部 | 文件 / 资产：导入、导出、格式转换、批量处理 | 🚧 待登记 |
| R2 执行型 | 外部 | 生成 / 转换：预览图、PDF、图片生成 | 🚧 待登记 |
| R2 执行型 | 外部 | 系统 / 设置：窗口、配置、快捷键 | 🚧 待登记 |
| R3 编排型 | 宿主 | 先检索再执行、批量多文档、多步工作流 | 🚧 当前无独立插件，建议宿主编排 |

结论：**R1 已有可用能力，R2 只有示例，R3 暂不单独实现**。三种角色先作为约束模型，不急着落成插件。

| 编号 | 方式 | 产出 | 现状 |
| --- | --- | --- | --- |
| CH1 | 文本框 | `I1` / `I2` | ✅ |
| CH2 | 文件选择 | `I3` / `I7` | 🚧 宿主 |
| CH3 | 拖拽 | `I3` / `I6` / `I7` | 🚧 宿主 |
| CH4 | 粘贴 | `I1` / `I3` / `I6` / `I7` | 🚧 宿主 |
| CH5 | 文件夹 / 批量 | `I4` / `I7` | 🚧 宿主 |

- 其余通道都需要宿主先归一化，chatllm 不直接接触输入设备。

## 7. 插件嵌套约束

### 7.1 编排方式（已确认宿主）

| 模式 | 做法 | 结论 |
| --- | --- | --- |
| A 宿主编排 | 插件返回“需要调用子插件”的建议，宿主执行 | ✅ **采用** |
| B 插件运行时内嵌 | 插件自己调用其它插件 | ❌ 暂不采用 |

理由：宿主可做超时、权限、确认与审计；插件内嵌会让调用链失控。

### 7.2 约束清单

| 约束 | 结论 | 说明 |
| --- | --- | --- |
| 最大深度 | **5 层** | 入口插件为第 1 层，超过拒绝 |
| 调用次数 | **不设上限** | 由深度、环、超时与预算兜底；宿主可另设总预算 |
| 环检测 | 调用链内 `lib_name + ffi_symbol` 去重 | 重复直接拒绝 |
| 权限继承 | 子插件权限 ≤ 父插件 | 不允许提权 |
| 白名单 | 插件需声明 `can_call` 或宿主维护允许列表 | 未声明不可调用 |
| 副作用 | `side_effects=1` 的子调用需宿主确认 | 只读可自动 |
| 单插件超时 | **15s** | 已确认 |
| 整链超时 | 由宿主控制，建议 120s | 次数不限，必须靠总超时兜底 |
| 预算 | 嵌套结果计入上下文预算 | 单条结果 ≤ 64 KiB |
| 审计 | 记录 `call_id`、`parent_call_id`、深度、耗时、状态 | 支持回放 |
| 失败传播 | 子插件失败不自动重试，返回父级 | 由模型或宿主决定 |
| 幂等 | 同一 `call_id` 只执行一次 | 防止重复副作用 |
| 并发 | 同链串行，不同对话可并行 | 避免资源竞争 |
| 数据边界 | 子插件不能读父插件未授权的资产 | 防越权 |
| 结果可信 | 子插件结果按不可信数据处理 | 防注入 |

### 7.3 调用记录

```text
{ call_id, parent_call_id, depth, lib_name, ffi_symbol,
  ok, elapsed_ms, result_size, error? }
```

## 9. 最终呈现效果

> chatllm 只负责产出数据，最终怎么渲染由宿主决定。下面是建议的呈现形态。

### 9.1 一轮对话结束后的界面

```text
┌──────────────────────────────────────┐
│ 主文本回答（content_html）            │
│                                      │
│ 这里可以出现 [图片 1] [导出文件] 占位  │
│                                      │
│ ┌────────┐ ┌────────┐ ┌──────────┐  │
│ │ 图片 1 │ │ 视频 1 │ │ 导出.pdf │  │
│ │ 缩略图 │ │ 播放器 │ │ 下载卡片 │  │
│ └────────┘ └────────┘ └──────────┘  │
│                                      │
│ ▸ 过程：检索 3 个能力，调用 2 个插件  │
│   （可折叠，默认收起）                 │
└──────────────────────────────────────┘
```

- **主文本**：始终存在，是回答主体；
- **附件**：按产生顺序排列，支持图片、视频、文件、音频；
- **过程**：检索 / 工具调用记录默认折叠，仅需要时展开；
- **状态**：截断、不支持格式、工具失败以一行提示展示，不打断正文。

### 9.2 数据形态

```json
{
  "content": "已导出并生成预览图",
  "content_html": "<p>已导出并生成预览图</p>",
  "attachments": [
    { "kind": "image", "ref": "asset://123", "mime": "image/png", "width": 1200, "height": 800, "source": "plugin" },
    { "kind": "file", "ref": "asset://124", "mime": "application/pdf", "name": "导出.pdf", "source": "plugin" }
  ],
  "usage": { "prompt_tokens": 1200, "completion_tokens": 300, "estimated": false },
  "context_truncated": { "history": true }
}
```

### 9.3 组合与顺序

- 文本是主字段，附件是补充，不用 Markdown 内嵌 base64；
- 正文需要引用附件时用 `[asset:123]` 占位，由宿主替换为组件；
- 未被正文引用的附件排在文末；
- 多个附件按 `attachments` 数组顺序展示。

### 9.4 失败与降级

| 情况 | 呈现 |
| --- | --- |
| 没有附件 | 退化为纯文本，与当前版本一致 |
| 附件缺失 / 失效 | 保留文本，省略该附件 |
| 插件执行失败 | 正文说明失败原因，过程区显示错误 |
| 上下文被裁剪 | 正文正常，状态区提示“历史已摘要” |
| 输入格式不支持 | 明确提示 `unsupported`，不猜测内容 |
