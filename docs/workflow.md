# chatllm 文档整理工作流

> 本文定义 chatllm 仓库文档从盘点、核对、撰写到回填的步骤，以及每一步需要什么反馈。
> 流程目标：**代码是唯一事实来源**，每步只产出可审阅的最小结果，确认后再进入下一步。

## 0. 基本原则

1. **事实优先**：文档描述必须能在代码、配置或脚本中找到依据；找不到依据的内容标为“待确认”，不凭印象补写。
2. **单一入口**：能力与构建入口在 `README.md`；模块与调用链在 `todo/README.md`；待办只在 `todo/TODO.md`。
3. **历史与现状分开**：设计稿保留原文，但在顶部标注“设计稿”与“现状以何处为准”。
4. **一次一步**：每个阶段结束提交一份可审阅的产物（清单、大纲或单篇 diff），反馈后再继续。
5. **不夹带代码改动**：文档整理阶段只改文档；发现的代码问题写入 `todo/TODO.md`，不在同一提交里修。

## 1. 步骤总览

| 阶段 | 动作 | 产出 | 反馈点 | 退出条件 |
| --- | --- | --- | --- | --- |
| S1 盘点 | 确认范围、读者与现有文档 | 范围说明 | 改哪些文档、给谁看 | 范围获确认 |
| S2 核对 | 从代码提取事实 | 事实清单（含证据路径） | 事实是否有遗漏 | 清单无异议 |
| S3 差异 | 文档与代码逐条比对 | 差异清单（过期/缺失/冲突） | 哪些先改、哪些暂缓 | 优先级获确认 |
| S4 结构 | 定文档树与各篇大纲 | 目录 + 大纲 | 结构是否合理、是否重复 | 大纲获确认 |
| S5 撰写 | 按篇修改，一次一篇 | 单篇 diff | 每篇内容是否准确 | 单篇获接受 |
| S6 校验 | 交叉检查链接、术语、版本、命令 | 校验结果 | 是否有遗留矛盾 | 校验通过 |
| S7 收口 | 更新入口、待办与外部回填 | 入口链接与状态 | 是否回填总库 | 入口可达 |

## 2. 各阶段说明

### S1 盘点范围

- **输入**：用户诉求、仓库现状、已有文档。
- **动作**：
  - 列出仓库内所有文档及其职责；
  - 确认本次是“校正现有文档”还是“新增文档集”；
  - 确认读者：开发者、FFI 调用方、运维/发布人员。
- **产出**：一句话范围 + 文档清单（路径、职责、状态）。
- **反馈问题**：
  1. 本次只改现有文档，还是允许新增 `docs/`？
  2. 读者以谁为主？
- **不要做**：不要在范围未定时直接重写全文。

### S2 从代码提取事实

- **输入**：`src/`、`setup.ts`、`dytes.json`、`Cargo.toml`、`.github/workflows/`、`ts/`、`tests/`。
- **动作**：按固定维度提取，每条记录“结论 + 证据文件”。
  - FFI 符号与请求/响应结构；
  - 存储位置、表结构、分片与迁移；
  - 外部依赖与加载路径；
  - 版本、构建命令、CI 与发布产物；
  - 测试前提与已知限制。
- **产出**：事实清单（建议表格：主题 / 结论 / 证据）。
- **反馈问题**：是否有只在运行环境中成立、代码里看不出的约定？
- **不要做**：不要根据旧文档反推代码行为。

### S3 生成差异清单

- **输入**：S1 的文档清单 + S2 的事实清单。
- **动作**：逐篇比对，按类型归档：
  - **过期**：描述与代码不一致；
  - **缺失**：代码有、文档无；
  - **冲突**：多处文档互相矛盾；
  - **冗余**：同一事实在多处重复。
- **产出**：差异清单，标注 `P0 必须改` / `P1 应该改` / `P2 可暂缓`。
- **反馈问题**：哪些条目本轮处理，哪些只登记到 `todo/TODO.md`？
- **不要做**：不要把“代码问题”和“文档问题”混在同一条。

### S4 确定结构

- **输入**：差异清单。
- **动作**：
  - 确定文档树与每篇职责；
  - 给每篇列标题级大纲；
  - 明确“事实只写一处，其他地方链接”。
- **产出**：文档树 + 各篇大纲。
- **反馈问题**：结构是否符合阅读路径？是否与外部总库重复？
- **不要做**：不要在结构未定时开始长文撰写。

### S5 分篇撰写

- **输入**：S4 的大纲 + S2 的事实。
- **动作**：
  - 一次只改一篇；
  - 保留必要的设计历史，但加“现状为准”标注；
  - 表格优先于长段落，命令必须可直接复制。
- **产出**：单篇 diff。
- **反馈问题**：这一篇是否准确、是否缺字段、是否需要示例？
- **不要做**：不要在同一轮顺带改其他篇。

### S6 交叉校验

- **输入**：已完成的各篇。
- **动作**：
  - 检查相对链接是否可达；
  - 检查同一术语、版本号、路径是否一致；
  - 检查命令与产物名是否匹配 CI 与 `dytes.json`；
  - 运行 `git diff --check`，检查代码块围栏配对。
- **产出**：校验结果（通过项 / 遗留项）。
- **反馈问题**：遗留项是修掉还是登记待办？
- **不要做**：不要用“看起来对”代替可核对的事实。

### S7 收口

- **输入**：校验通过的文档。
- **动作**：
  - 更新 `README.md` 的文档入口；
  - 更新 `todo/TODO.md` 的完成项与新增项；
  - 按需回填 `dytes_sys_operations/sysinfo/sys/chatllm/`；
  - 一次提交只包含本轮文档改动。
- **产出**：入口链接 + 状态更新 + 提交。
- **反馈问题**：是否同步外部总库？提交信息用什么范围？
- **不要做**：不要在没有确认的情况下删除历史文档。

## 3. 反馈方式

每一步用同一张“反馈卡”，避免开放式讨论：

```text
阶段：S3 差异清单
产物：<文件路径或 diff 摘要>
待确认：
  1. P0 条目 A / B 是否本轮处理？
  2. C 条目是否只登记待办？
请回复：接受 / 修改（指出条目）/ 跳过
```

规则：

- 未收到反馈，不进入下一阶段；
- 反馈为“修改”时，只改被点名的条目，其余保持不动；
- 同一阶段最多迭代两轮，仍无结论则降级为 `todo/TODO.md` 条目。
